# CIがいつも1分強かかる理由

`.github/workflows/ci.yml`（GitHub Actions）が毎回だいたい1分〜1分半かかる理由の解説。
特別遅いわけではなく、典型的な所要時間。

---

## 内訳

CIの1回の実行は、大きく分けて3段階:

1. **ランナーの起動**: GitHub ActionsはPRごとに毎回まっさらなUbuntu仮想マシンを
   新規に立ち上げる（前回の状態は一切引き継がない）。VM起動・`actions/checkout`・
   `actions/setup-python`だけでも数十秒かかる。
2. **依存パッケージのインストール**: `pip install -e ".[dev]"`で`chromadb`・
   `streamlit`・`python-docx`等、比較的重いパッケージ一式を毎回入れ直す。
   `cache: "pip"`（`actions/setup-python`のオプション）でpipのダウンロード
   キャッシュは効いているが、ゼロからのインストールに比べて速くなっているだけで
   「一瞬」にはならない。
3. **実行**: `ruff check .` → `mypy` → `pytest -m "not needs_llm"` を順番に実行。
   このプロジェクトの規模（数千行）ならここ自体は数秒〜十数秒程度。

体感的に一番重いのは2（依存インストール）。

## なぜ「毎回」やり直すのか

CIは「このコミットが本当にクリーンな環境で動くか」を保証するのが目的。開発者の
ローカル環境（既にインストール済みのパッケージ、ローカルだけの設定ファイル等）に
依存した「手元では動くのにCIでは落ちる」を防ぐため、あえて何も引き継がない
まっさらな環境で毎回検証する。これは効率より正しさを優先する設計。

## 高速化の余地（やっていないこと）

- 依存関係をもっと絞る（今は本体+dev extrasを毎回フルインストール）
- Draft PRではCIを走らせない設定にする
- セルフホストランナー（起動が速い）に変える
- 依存関係のバージョンを固定してDockerイメージ化し、イメージごとキャッシュする

このプロジェクトの規模・用途（ポートフォリオ用の個人開発）ではオーバーエンジニア
リングになるため、あえて手を入れていない。

## 補足

CIの1回あたりの所要時間自体は正常な範囲（約1分〜1分半）。小さな変更を細かく
PRに分けて開発を進めるスタイルだと、その分だけCIを待つ回数が増える。1回あたりが
遅いわけではなく、回数の掛け算で体感時間が伸びる、という点は覚えておくとよい。
