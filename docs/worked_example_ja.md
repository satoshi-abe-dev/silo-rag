# 具体例：1つの質問が回答になるまで

日本語 | [English](worked_example_en.md)

質問が、各段階でどのように加工されて回答になるかを、**実際の値**で追う。用語（BM25、ベクトル検索）は
[README の「用語：BM25とベクトル検索」](../README_ja.md#用語bm25とベクトル検索)を先に読むと分かりやすい。

## 前提

- データは合成データ（ダミーの社内プロジェクトレポート60件）。
- モデルは、クエリ作成・並べ直し・回答生成が`qwen2.5-7b-instruct`、埋め込みが`text-embedding-nomic-embed-text-v1.5`
  （どちらもLM Studio）。
- 値は、2026年10月に、使い捨てのスクリプトで取った（リポジトリには含めていない）。`search()`の中身を1段階ずつ再現し、
  最後に本物の`search()`の結果と一致することを確かめてある。**LLMを含む段階は、温度0でも、実行のたびに少し変わる**
  （同じ質問から出てくるクエリの言葉や区切りが、回によって変わった）。値は「ある1回の実行」として読んでほしい。

## 全体の流れ

| 段階 | 入力 → 出力 |
| --- | --- |
| 0. 取り込み（事前に1回） | レポートのファイル → 見出しごとのチャンク → チャンクごとのベクトル（768個の数値） |
| 1. クエリ作成（LLM） | 質問 → 検索クエリ（探したい内容の言葉だけ） |
| 2. BM25 | クエリ → 言葉が一致するチャンクの点数（上位20件） |
| 3. ベクトル検索 | クエリ → 意味が近いチャンクの点数（上位20件） |
| 4. 混ぜる | 2つの点数を0〜1にそろえて、0.5ずつで足す → 上位20件 |
| 5. 並べ直し（LLM） | 20件の候補 → 質問への関連度順 → 上位5件 |
| 6. 回答生成（LLM） | 上位5件のチャンク → 出典つきの回答 |

2〜5が、検索（ノードC）の`search()`の中身。1は、エージェント（ノードG）の`plan`ノードが、`search()`に渡す前に行う
（通常方式には、この段階がなく、質問がそのまま`search()`に渡る）。6が回答生成（ノードD）。

## 0. 取り込み：レポート1件が、チャンクとベクトルになる

`RPT-018.md`（経営企画部、マーケティング施策、テーマ「予算策定プロセス見直し」）の場合。ファイルの先頭にある情報
（メタデータ）と、見出しごとに区切った本文（チャンク）に分ける。

メタデータ（全チャンクに付く）: `report_id=RPT-018`、`dept=経営企画部`、`project_type=マーケティング施策`、
`subject=予算策定プロセス見直し`、`method=アジャイル（スクラム）`、`date=2024-06-03` など。

| チャンクID | 本文（先頭） |
| --- | --- |
| `RPT-018::プロジェクト目的` | 【プロジェクト目的】マーケティング施策における予算策定プロセスの見直しを行い、より効率的かつ柔軟な予算管理を実現すること。 |
| `RPT-018::対象領域・テーマ` | 【対象領域・テーマ】マーケティング施策においての予算策定プロセス全体。 |
| `RPT-018::与件` | 【与件】現行の予算策定プロセスは詳細な見直しが求められ、過去のプロジェクトで予算超過が複数発生していること。 |
| `RPT-018::教訓・つまずいたポイント` | 【教訓・つまずいたポイント】予算超過に気づくのが遅れ、プロジェクトの半分経過時点で総予算の120%を使用していた。… |
| （ほか4つ） | 実行計画、主要リソース、採用手法、成果サマリー |

このレポートは8つのチャンクになる。各チャンクは、埋め込みモデルで**768個の数値の並び**（ベクトル）に変わり、
ChromaDBに保存される。例えば`RPT-018::プロジェクト目的`のベクトルは、先頭の4つが`[0.010, 0.018, -0.132, 0.031]`
（残りの764個は省略）。意味が近い文は、数値の並びも近くなる。BM25の方は、チャンクの本文そのものを使う
（検索のたびに、全チャンクから計算し直す）。

## 例1：うまくいく質問（QA-005）

> **質問**: 予算策定プロセス見直しのマーケティング施策で、過去に参考になる社内事例はありますか？
> 実施条件や注意点も教えてください。
>
> **正解のレポート**: RPT-018（経営企画部）

### 1. クエリ作成

| | 内容 | 検索に使う断片の数 |
| --- | --- | --- |
| 質問 | （上のとおり） | 58個 |
| クエリ | 予算策定プロセス見直し マーケティング施策 社内事例 実施条件 注意点 | 26個 |

「〜はありますか？」「教えてください」が消えて、探したい内容の言葉が残る。
（断片の数は、検索の前処理で数えたもの。日本語は、重なりを許して2文字ずつ（「予算策定」→「予算」「算策」「策定」）、
英数字の語は1つ、として数える。）

### 2〜4. BM25、ベクトル検索、混ぜる

| 順位 | BM25（点数） | ベクトル検索（点数＝距離にマイナスを付けたもの） | 混ぜた結果（合計＝BM25側＋ベクトル側） |
| --- | --- | --- | --- |
| 1 | RPT-018::対象領域・テーマ（123.8） | RPT-018::プロジェクト目的（-0.353） | RPT-018::プロジェクト目的（0.98＝0.96＋1.00の平均） |
| 2 | RPT-018::プロジェクト目的（122.4） | RPT-018::与件（-0.410） | RPT-018::対象領域・テーマ（0.74） |
| 3 | RPT-016::対象領域・テーマ（105.6） | RPT-056::プロジェクト目的（-0.410） | RPT-018::与件（0.40） |
| 4 | RPT-018::与件（97.8） | RPT-035::プロジェクト目的（-0.415） | RPT-035::プロジェクト目的（0.36） |
| 5 | RPT-025::プロジェクト目的（96.8） | RPT-044::実施条件（-0.419） | RPT-025::プロジェクト目的（0.33） |

- BM25の点数は、言葉の一致で決まる絶対値（そのままでは、ベクトル側の点数と足せない）。ベクトル検索の点数は、
  距離が小さいほど大きい。そこで、それぞれ上位20件の中で**最小〜最大が0〜1になるようにそろえて**から、0.5ずつで足す。
- 混ぜた結果の1位は、BM25で2位、ベクトルで1位のチャンク。両方の得点が高いものが上がる。

### 5. 並べ直し（LLM）

混ぜた上位20件を、LLMが質問への関連度で並べ直し、上位5件を選ぶ（並べ直しのLLMに渡すのは、**書き直し後のクエリ**。
回答生成のLLMには、元の質問が渡る）。

1. RPT-018::プロジェクト目的 2. RPT-018::与件 3. RPT-015::対象領域・テーマ 4. RPT-035::プロジェクト目的
5. RPT-016::対象領域・テーマ

混ぜた結果の上位5件にはなかった`RPT-015`が、3位に入った（20件の候補の中から、LLMが選んだ）。

### 6. 回答生成（LLM）

上位5件のチャンクだけを根拠に、回答を作る。本文中の「（RPT-018）」のような引用は、LLMが書く。それとは別に、出典の
一覧が、上位5件のチャンクのメタデータから機械的に作られる（レポートとセクションの組で重複を除く）。

> マーケティング施策における予算策定プロセス見直しの参考となる社内事例としては、経営企画部で実施された
> 「マーケティング施策における予算策定プロセスの見直し」（RPT-018）があります。このプロジェクトでは、詳細な見直しが
> 求められており、過去のプロジェクトで予算超過が複数発生していました（RPT-018）。…（以下略）

出典の一覧は5件で、RPT-018（経営企画部）の2つのセクション、RPT-015（経営企画部）、RPT-035（経営企画部）、
RPT-016（商品開発部）。正解のRPT-018が入っている。

## 例2：うまくいかない質問（QA-001）

> **質問**: 経営企画部です。既存商品リニューアルに似たテーマでマーケティング施策を検討しています。他部署で参考になり
> そうな過去のマーケティング施策の事例はありますか？特に気をつけるべき落とし穴があれば教えてください。
>
> **正解のレポート**: RPT-041（商品開発部）

### 1. クエリ作成

| | 内容 | 断片の数 |
| --- | --- | --- |
| 質問 | （上のとおり） | 101個 |
| クエリ（7B） | 経営企画部既存商品リニューアルマーケティング施策落とし穴 | 27個 |
| （参考）クエリ（32B） | 既存商品リニューアル マーケティング施策 落とし穴 | 20個 |

7Bは、質問者の部署名「経営企画部」をクエリに残した（プロンプトでは、残さないよう指示している）。32Bは残さなかった。
なお、同じ7Bで、別の回に同じ質問を通したときは、「経営企画部 商品リニューアル マーケティング施策 落とし穴」と、
スペースを入れ、「既存」を落とした形で出てきた（どちらも「経営企画部」は残っている）。

### 2〜4. BM25、ベクトル検索、混ぜる

BM25では、**正解のRPT-041が、クエリの書き直しで3位から1位に上がった**（質問そのまま：3位、7Bのクエリ：1位、
32Bのクエリ：1位）。

| 順位 | BM25（点数） | ベクトル検索（点数） | 混ぜた結果（合計＝BM25側＋ベクトル側） |
| --- | --- | --- | --- |
| 1 | **RPT-041::成果サマリー**（117.8） | RPT-017::推進体制（-0.299） | RPT-017::推進体制（0.50＝0.01＋1.00の平均） |
| 2 | RPT-018::対象領域・テーマ（112.7） | RPT-042::推進体制（-0.309） | **RPT-041::成果サマリー**（0.50＝1.00＋0.00の平均） |
| 3 | RPT-016::対象領域・テーマ（111.9） | RPT-005::主要リソース（-0.342） | RPT-042::推進体制（0.48） |
| 4 | RPT-027::成果サマリー（109.9） | RPT-048::推進体制（-0.345） | RPT-005::主要リソース（0.41） |
| 5 | RPT-025::主要リソース（108.8） | RPT-019::推進体制（-0.358） | RPT-048::推進体制（0.37） |

ベクトル検索の上位には、質問と関係の薄い「推進体制」のチャンクばかりが並び、**RPT-041は入っていない**。
混ぜた結果では、RPT-041は2位に残った。

### 5. 並べ直し（LLM）

並べ直しのあとの上位5件は、次のとおりで、**RPT-041が消えた**。

1. RPT-018::対象領域・テーマ 2. RPT-025::主要リソース 3. RPT-019::推進体制 4. RPT-048::推進体制
5. RPT-023::対象領域・テーマ

候補の2位にいた正解を、7Bの並べ直しが、上位5件から落とした。

### 6. 回答生成（LLM）

> 該当する事例が見つかりません（RPT-018, RPT-025は経営企画部の予算策定プロセスに関するもので、…）。…（以下略）

この質問は、**検索（候補を集める段階）では成功していて、並べ直しで失敗した**。クエリの書き直しだけを見ても、
原因は分からない例になっている。

## どの段階で、書き直しが効いているか（7B、15問）

質問を検索クエリに書き直すと、7Bの最終的な当たり率は 0.60 → 0.93 に上がった。どの段階で効いているかを、
15問すべてで、段階ごとに調べた。数字は、「正解のレポートが入った問数（15問中）」。

**検索の各段階（並べ直しの前。LLMは使っていない）**

| 段階 | 質問そのまま | 7Bのクエリ | 32Bのクエリ |
| --- | --- | --- | --- |
| BM25だけ・上位5件 | 11 | **15** | **15** |
| ベクトル検索だけ・上位5件 | 5 | 5 | 7 |
| 混ぜた直後・上位5件 | 10 | 12 | 11 |
| 混ぜた上位20件（並べ直しの候補） | 15 | 15 | 15 |

- **BM25は、書き直しで大きく良くなった**（11 → 15）。ただし、書き直しでは、余計な言葉が減るだけでなく、言葉の選び方や
  区切りも変わる（例えば、7BのQA-001のクエリは「既存」を落としている）。「余計な言葉を除いたから」が理由かどうかは、
  確かめていない（その部分だけを切り出す実験はしていない）。
- **ベクトル検索は、合計では変わらず**（5 → 5）、もともと当たりにくい（5〜7問）。ただし、問ごとには、2問で当たりが増え、
  2問で減っていて、入れ替わっているだけ。順位や点数は、混ぜるときにも使われるので、上位5件の当たりが変わらなくても、
  混ぜた結果には影響しうる。
- **並べ直しの候補20件には、書き直す前から、15問すべてで正解が入っていた。** つまり、取りこぼしが起きるのは、
  候補を集める段階ではなく、候補から上位5件を選ぶ段階。

**最終の上位5件（並べ直しのあと）。候補を集めるクエリと、並べ直しに使うクエリを入れ替えた**

| | 並べ直し：質問そのまま | 並べ直し：書き直し後 |
| --- | --- | --- |
| **候補集め：質問そのまま**（通常方式） | 9 | 12 |
| **候補集め：書き直し後** | **15** | 14（エージェントの既定） |

- 書き直したクエリは、BM25とベクトル検索の両方に同時に渡るので、この結果を「BM25だけの効果」とは言えない。
- 候補を書き直し後のクエリで集めると、大きく良くなる（9 → 15）。並べ直しに書き直し後のクエリを使うだけでも、
  良くなる（9 → 12）。両方を書き直しにしても、足し算にはならない（14）。
- 最も良かったのは、「候補は書き直し後のクエリで集め、並べ直しは元の質問で行う」組み合わせ（15）。例2（QA-001）は、
  この組み合わせだと、正解が上位5件に残る。元の質問の方が、並べ直しのLLMに、質問者の意図（他部署の事例がほしい、など）を
  伝えられるのかもしれないが、確かめていない。**1問の差なので、この組み合わせを採用してはいない。**

## 注意点

- **7Bだけの結果**（32Bは、BM25とベクトル検索の段階だけ。並べ直しのLLMを通していない）。
- **15問・各1回**。LLMの出力は、実行のたびに少し変わる。1問の差は、断定できない。
- 「書き直しが効いた理由」は、段階ごとの数字から言えることまでしか書いていない。例えば、「並べ直しの段階で、短いクエリの
  方がLLMが判断しやすい」という説明は、まだ確かめていない。
