# 仕組みの詳細：ノードと検索

日本語 | [English](architecture_en.md)

[README](../README_ja.md#アーキテクチャ)の図に出てくる、8つのノード（処理のまとまり。それぞれ1ファイル）の役割と、検索（ノードC）の仕組みを説明する文書。READMEの図を先に見ておくと、読みやすい。

この文書で分かること:

- 各ノードが何をして、どのAIモデルを使うか
- オプションのノードG・Hが、ほかのノードのどの関数を呼ぶか
- 検索で使う、2つの方法（キーワード検索のBM25と、意味で探すベクトル検索）と、その組み合わせ方

## 各ノードの役割と、使うモデル

使うモデルの名前（`llm_model`など）は、`config.toml`の`[ai]`で設定する。

| ノード | ファイル | 役割 | 使うモデル |
| --- | --- | --- | --- |
| A | `src/silo_rag/datagen.py` | - デモ用の振り返りレポートを合成する（部署ごとに書き方・ファイル形式を変え、成果の画像も埋め込む）<br>- 評価用の質問と正解を作る | `llm_model`（レポート本文の生成） |
| B | `src/silo_rag/ingest.py` | - レポートを見出しごとに分ける（チャンク。5形式に対応）<br>- 埋め込まれた画像を、画像を読めるAI（VLM）で説明文にする<br>- チャンクを数値の並び（ベクトル）に変えて、ChromaDBに入れる | - `embed_model`（チャンクのベクトル化）<br>- `vlm_model`（画像の説明文） |
| C | `src/silo_rag/retrieval.py` | - キーワード検索（BM25）と意味検索（ベクトル検索）を組み合わせて探す<br>- 候補を、LLMで並べ直す<br>- 会話履歴を見て、「それ」などの指示語を具体的な言葉に直す<br>- （オプション）検索の前に、質問から検索クエリを作る（`[retrieval] rewrite_query`。既定はオフ） | - `embed_model`（質問のベクトル化）<br>- `llm_model`（並べ直し・指示語の解決・検索クエリの作成） |
| D | `src/silo_rag/generation.py` | - 見つけたチャンクを根拠に、回答を作る<br>- 出典（レポートID・セクション・部署）を付ける<br>- 会話履歴を見て、指示語を解決する | `llm_model`（回答の生成） |
| E | `src/silo_rag/eval.py` | - 検索の精度を測る（Recall@k、MRR）<br>- 回答の品質を測る（LLMによる採点、正解の引用率）<br>- 指標の意味は、[評価の詳細](agent_evaluation_ja.md#表の読み方)を参照 | - C・Dが使うすべてのモデル<br>- `llm_model`（採点） |
| F | `src/silo_rag/app.py` | - 画面（Streamlitのチャット画面）<br>- 部署・プロジェクト種別での絞り込み、出典の表示 | C・Dが使うすべてのモデル（質問のたびに呼ぶ） |
| G（オプション） | `src/silo_rag/agent.py` | - LangGraphで、「検索クエリの作成 → 検索 → 判定 → 別の切り口でクエリを作成 → 再検索」を回す<br>- 詳しくは、[エージェント方式の設計](agent_ja.md#ノードglanggraphエージェント) | C・Dが使うすべてのモデル |
| H（オプション） | `src/silo_rag/langchain_adapter.py` | - 自前の検索を、LangChainの部品（Retriever）として使えるようにする<br>- LangChain既製のエージェントで答え、Gと比べる<br>- 詳しくは、[エージェント方式の設計](agent_ja.md#ノードhlangchain連携) | C・Dが使うすべてのモデル |

`vlm_model`を読み込んでいないときは、Bの画像の説明文だけが飛ばされる（警告が出るだけで、ほかは動く）。

## G・Hが呼ぶ、C・Dの関数

G・Hは、C・Dの中にあるのではなく、C・Dの公開されている関数を呼ぶ、別のノード。

- **G**（`agent.py`）: Cの`search`（検索）・`plan_query`（検索クエリの作成）・`rerank`（並べ直し）と、Dの`answer_question`（回答の作成）を呼ぶ
- **H**（`langchain_adapter.py`）: Cの`search`と、Dの`Answer`（回答の型）・`build_citations`（出典の作成）を呼ぶ
- どちらも、使うときだけ読み込む（`import`する）。LangGraph・LangChainが入っていなくても、通常方式は動く

## 検索の仕組み：BM25とベクトル検索

Cは、性質の違う2つの検索を組み合わせている。

- **BM25（キーワード検索）**: 「質問の言葉が、どの文書に、どれだけ出てくるか」で点数を付ける**計算式**。AIモデルではなく、学習もしない
  - 言葉が文書に多く出るほど高い（頭打ちあり）。どの文書にも出る言葉（「です」「ます」）はほとんど効かず、珍しい言葉（「予算策定」）は大きく効く。長い文書は少し割り引く
  - 得意: 型番・固有名詞・専門用語のように、**言葉そのものが一致する**探し方
  - 苦手: 言い換え（「予算」と「費用の見積もり」）を同じものと見なせない。検索と関係の無い言葉が質問に混ざると、その言葉を含む文書の点数が上がり、順位に影響することがある（索引に1つも無い言葉は0点で、何も変えない）
- **ベクトル検索（意味検索）**: 埋め込みモデル（AIモデル）で文を数値の並びに変え、**意味が近いか**を距離で測る。言い換えに強い
- **点数の統合**: 両方の点数を、それぞれ0〜1に**正規化**してから、`vector_weight`（既定0.5）の割合で合算し、上位の候補をLLMが並べ直す
  - 正規化: 最高点を1、最低点を0として、間を比例して直す。例外: 最高点と最低点の差がほぼ0なら全員1。キーワード検索は、最高点が0以下なら全員0（こちらを先に判定）
  - 実際の数字での計算例は、[具体例](worked_example_ja.md)
- **このプロジェクトでの扱い**: 前処理は簡単な方法にした（形態素解析は使わない）。日本語は、重なりを許して**2文字ずつ**に区切り（「予算策定」→「予算」「算策」「策定」）、英数字の語・ID（`RPT-014`など）は、**1語のまま小文字にする**（`rpt-014`）。`rank_bm25`の`BM25Plus`を使う。`BM25Okapi`は、半数を超える文書に出る言葉の重み（IDF）が負になることがあり、小さなデータで実際に起こるため替えた
