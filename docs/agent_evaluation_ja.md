# エージェント方式の評価

日本語 | [English](agent_evaluation_en.md)

通常方式と、エージェント方式（ノードG）と、LangChain既製のエージェント（ノードH）の精度を、同じ質問セットで比べた結果。方式の違いや設定の意味は、[エージェント方式の設計](agent_ja.md)にある。

## 要点

- **15問**: 7Bのモデルでは、エージェント方式（検索クエリを作ってから1回検索）が、通常方式より大きく良く見えた（hit_rate 0.60 → 0.93）。ただし、この15問は、設計を決めるときに見ていた質問で、設計がこの15問に合っていた可能性が高い
- **45問で測り直すと、差は偶然の範囲**: 通常方式で、検索クエリの作成なし→ありを比べると、7Bで0.71 → 0.76、32Bで0.76 → 0.80。7Bのエージェント方式の既定も0.76。質問ごとに、良くなった数と悪くなった数を数えると、偶然でも起こる程度の差だった
- **結論**: 回答方式の既定は、通常方式のまま。検索クエリの作成（`[retrieval] rewrite_query`）も、オフのまま

## 表の読み方

| 言葉 | 意味 |
| --- | --- |
| hit_rate | 最終の検索結果（上位5件）に、正解のレポートが入った質問の割合。高いほど良い |
| 部署横断 / 自部署 | 部署をまたいだ質問だけ / 同じ部署の質問だけで数えた、hit_rate |
| MRR | 正解のレポートの順位の逆数（1位なら1、2位なら0.5、入らなければ0）の平均。高いほど、正解が上位に来ている |
| 引用率 | 回答の本文が、正解のレポートのIDを引用した質問の割合 |
| judge | LLMが、回答を正解の根拠と見比べて付けた点数（1〜5）の平均 |
| 検索回数 / LLM呼び出し / 秒/問 | 1問あたりの平均。費用と時間の目安 |
| 7B / 32B | 使ったモデルの大きさ（7B = `qwen2.5-7b-instruct`、32B = `qwen2.5-coder-32b-instruct-mlx`。いずれもLM Studio、4bit） |
| G strict / G lenient | エージェント方式で、根拠が足りるかの判定を厳しくしたもの / 甘くしたもの |
| クエリ作成 | 1回目の検索の前に、LLMが質問から検索クエリを作る（`first_query = "rewrite"`） |
| 1検索 | 検索を1回に限る（`max_attempts = 1`。判定と再検索をしない） |

## 15問での比較

- 以下の表は、同じ評価セット（15問、うち部署横断5問）を、各方式1回ずつ回した結果。**この15問は、検索クエリの作成の設計を決めるときに見ていた質問と同じで、設計がこの15問に合っていた可能性が高い**（45問での測り直しは、下に載せた）
- 「LLM呼び出し」は、回答までのチャット呼び出し回数（埋め込みとjudgeは含まない）。「上限での判定の省略」の前に測ったため、上限に達した質問ごとに、実際は1回少ない
- judgeの採点には回答と同じモデルを使うため、**judgeは同じモデルの行どうしでしか比べられない**

### 分かったこと

- **15問では、「再検索」ではなく「質問から検索クエリを作ること」が効いているように見えた（7B）。** 質問そのままで検索する版は、再検索を足しても0.60→0.67〜0.73にとどまった。1回目から検索クエリを作らせると0.80〜0.93になり、**再検索を1回に制限しても（0.93）劣らなかった**。部署横断も0.40→0.80に上がった。どの段階で効いたかの切り分けは、[具体例](worked_example_ja.md)にある（これも15問での結果）。**ただし、45問で測り直すと、この効果は確認できなかった**（下の「45問での測り直し」）
- **この切り分けは、LangChain既製エージェントに負けたことがきっかけだった。** 既製エージェントは、検索回数を増やさずに0.93を出した。調べると、LLMが毎回、要点だけのクエリを作ってから検索していた。最初の仮説「再検索で補える」は、半分しか合っていなかった
- **32Bでは、どの工夫も、はっきりした効果が見えない。** 通常方式がすでに0.87で、クエリ作成＋1検索が0.93（1問差）。部署横断は1.00→0.80（1問差）に下がり、再検索まで付けると0.60に下がった
- **結論: 回答方式の既定は通常方式のまま。エージェントは、15問では小さいモデルで有利に見えたが、45問では通常方式との差を確認できなかった。** エージェントの既定は、15問の測定で最も良かった`first_query = "rewrite"`＋`max_attempts = 1`にした（表の「クエリ作成＋1検索」の行）。7Bで45問に測り直すと、この既定は、通常方式で検索クエリの作成をオンにしたものと同じ動きで、差は偶然の範囲だった（下の「45問での測り直し」）。再検索のループは、`max_attempts`を増やせば使えるが、クエリ作成への上乗せ効果は、どちらのモデルでも確認できなかった。大きいモデルでは、通常方式を使う
  - 既定に切り替えたあと、7B・32Bで回し直し、質問ごとの当たり・外れとhit_rateなどが一致することを確認した。LLM呼び出しは、上限での判定の省略により、表の4.0回から3.0回に減った

## 45問での測り直し（通常方式。検索クエリの作成なし・あり）

通常方式の`search()`に、検索クエリの作成（`rewrite_query`）をオンにした場合と、7Bでエージェント方式の既定（`first_query = "rewrite"`・`max_attempts = 1`）を、質問を45問に増やして測った。各条件1回ずつ。

| モデル・方式 | hit_rate | 部署横断 | 自部署 | MRR | 引用率 | judge | LLM呼び出し | 秒/問 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 7B・クエリ作成なし | 0.71 | 0.60 | 0.77 | 0.50 | 0.64 | 3.80 | 2.0 | 10.8 |
| 7B・クエリ作成あり | 0.76 | 0.60 | 0.83 | 0.52 | 0.67 | 3.73 | 3.0 | 10.8 |
| 7B・エージェントの既定（クエリ作成＋1検索） | 0.76 | 0.60 | 0.83 | 0.52 | 0.71 | 3.78 | 3.0 | 11.7 |
| 32B・クエリ作成なし | 0.76 | 0.47 | 0.90 | 0.57 | 0.69 | 3.11 | 2.0 | 49.3 |
| 32B・クエリ作成あり | 0.80 | 0.60 | 0.90 | 0.61 | 0.73 | 2.93 | 3.0 | 50.5 |

- **質問**: 45問（部署横断15、自部署30）。レポートの仕様から機械的に作った（LLMは使っていない）。15問の評価と同じレポート・同じ作り方で、13問は15問と同じ問文、32問は新しい問文
- **hit_rateの変化を、質問ごとに数えると、差は偶然の範囲**（符号検定）
  - 7B: 良くなった7問、悪くなった5問（p=0.77）
  - 32B: 良くなった6問、悪くなった4問（p=0.75）。部署横断は0.47→0.60だが、良くなった4問、悪くなった2問（p=0.69）
- **15問と同じ13問に絞ると改善が見え、新しい32問に絞ると見えない。** 良くなった／悪くなった: 7Bは13問で4／0、新しい32問で3／5。32Bは13問で2／0、新しい32問で4／4。15問で大きく見えた改善は、その15問に合わせて調整したために、大きく見えていた可能性が高い
- **費用**: LLM呼び出しは、1問あたり2.0回から3.0回に増える。所要時間は、ほぼ同じ（7B 10.8→10.8秒、32B 49.3→50.5秒）
- **エージェント方式の既定は、通常方式で検索クエリの作成をオンにしたものと、同じ動きだった（7B）。** 検索結果は45問中44問で順序まで同じ、当たり・外れは45問すべてで同じ（1問だけ、LLMのばらつきで少し違った）。検索を1回に限ると、判定も再検索も起きず、「クエリを作る→検索→回答」だけになるため。したがって、通常方式に対する差は、上のクエリ作成と同じで、偶然の範囲（良くなった7問、悪くなった5問、p=0.77）。32Bは、構造が同じなので、測っていない。再検索のループ（`max_attempts`を増やす）は、45問では測っていない
- **結論**: 効果を確認できなかったので、`[retrieval] rewrite_query`は、オフのまま

> ⚠️ **どの結果も、各条件1回の測定。差が1問分（15問では0.07、45問では0.02）の比較は、断定できない。この質問セットでの「傾向」を示すもの。**
>
> - 温度0でも、完全な再現は保証されない。ばらつくのは、回答文を作る段階（引用率・judge）と、LangChain既製エージェントの検索（ツールに渡すクエリを、毎回LLMが温度0.2で作る）
> - 既製エージェントのばらつきは、途中で止めた複数回の実行で観察したことで、保存してあるのは最後の1回分だけなので、数字では裏付けていない
> - 検索の結果が再現することは、別の質問セットでも同じ結果になることを意味しない。実際に、15問に合わせて決めた検索クエリの作成は、45問（新しい32問を含む）では効果が見えなかった
> - Gemma 4 26B（思考モデル）は、1問あたり約174秒かかったため、途中で打ち切り、比較に含めていない

## 開発中に見つけた問題

- **独立レビュー（codex）の指摘3件**: CIが、エージェント用の追加ライブラリ（LangGraphなど）を入れていない／再検索が前回までの根拠をすべて押し出す／判定に会話履歴が無い。いずれもモックで再現して修正し、回帰テストを足した
- **実LLM（7B）での動作確認で見つけた3件**（モックのテストだけでは見つからなかった）: 判定が厳しすぎて毎回上限まで再検索する／再検索用に作ったクエリに質問者自身の部署名が入る／再検索の結果を交互に並べる方式が、元の質問で拾えていた正解を押し出す（集めた候補全体を元の質問で並べ直す`select`ノードで解消）
- **評価で見つけた設計の誤り**: 「再検索が効く」という最初の仮説は、半分しか合っていなかった。さらに、「検索クエリの作成が効く」という次の結論も、15問に合わせた調整のせいで、強すぎた（45問で測り直して分かった）
